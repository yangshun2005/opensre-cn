# CI/CD 可靠性计算

使用以下定义从原始 GitHub 记录计算报告。
返回指标值时，同时给出分子、分母、单位、覆盖状态和证据链接。

## 统计总体与覆盖

在 UTC 时间下固定 `[start, end)`。统计该窗口内默认分支上或针对 `pull_request` / `pull_request_target` 事件创建的唯一工作流运行 ID。保持两个总体分开，并对它们的并集去重作为 `executions`。`pr_executions` 统计 PR 工作流运行数，而非 Pull Request 数。

使用截至 `end` 观察到的结果。合格运行的最新结论为 `success`、`failure`、`timed_out`、`startup_failure` 或 `action_required`。后四者为失败。单独报告被排除的 pending、cancelled、skipped 和 neutral 运行；它们未计入比率不代表成功。

为重跑 ID 获取更早的尝试。按 `(run_id, run_attempt)` 去重尝试，并将其保留为历史，而非额外执行。仅凭较晚的尝试编号不能证明更早的失败。匹配历史时使用稳定的工作流 ID 和 PR 编号加 head 仓库；一个绿色的 Security 工作流无法弥补失败的 CI 工作流。

合并 PR 影响覆盖窗口内合并的 PR。将运行与其实际 PR 和作者关联，包括 Fork 和复用的分支名。获取建立初始分支状态和相关 PR 等待所需的窗口前历史；边界记录不计入窗口内执行数。

记录分页完成情况、已获取的总体、被排除的结果，以及任何缺失的尝试、PR 关联或边界状态。确定每个缺口影响哪些指标。提交级历史的完整性不能证明窗口完整性，空的成功查询与失败的查询不同。

## 失败计数与比率

若任一已获取的尝试失败，`pr_failures` 对每个合格的 PR 运行计一次，包括最新尝试通过但更早尝试失败的运行。截至 `end`，按其工作流和 PR 历史中首次后续成功对每个失败运行分类：

- `reliability_failures`：观察到失败后在同一 SHA 上成功，在该运行的尝试内或后续运行中。
- `source_failures`：首次后续成功使用不同的 SHA。
- `unresolved_failures`：未观察到后续成功。

这些是基于结果的类别。报告中的 **CI-caused** 标签指同 SHA 恢复代理；它不确立根因。成功前 SHA 变化同样不能证明源代码导致失败。历史缺失使分类不可用，而非未解决。

计算 `pr_failure_rate = 100 * pr_failures / pr_executions` 和 `ci_failure_rate = 100 * reliability_failures / pr_executions`。同时报告可靠性失败占失败 PR 运行的比例。分母为零时为 `N/A`，而非零比率。

## 正常工作流时长

对每个工作流，`normal_minutes` 是计入总体中成功首次尝试的执行时长中位数。使用尝试开始和完成时间；必要时获取作业完成时间。若使用 `updated_at` 作为完成代理，需披露该近似。

**最慢的正常运行** 是这些每工作流中位数中的最大值，附其工作流名称和样本数。没有成功首次尝试的工作流没有实测基线；披露缺失的基线。

## 默认分支红灯时间与恢复

使用默认分支 `push` 运行按时间顺序重建观察到的分支状态。跟踪当前提交及其工作流尝试；被取代提交的迟到结果不得改变分支状态。如适用，说明使用运行创建时间作为推送时间代理。

当前提交上的观察到失败开启一个红灯区间。当该提交或其后继提交的所有适用工作流均成功完成时关闭。Pending 或被排除的结果不确立绿色。一旦后继提交完全绿色，仅在较旧提交上运行的工作流不会使分支保持红灯。使用尝试历史捕获红灯后转绿的重跑，即使最新运行列表完全成功。

将已知红灯状态跨越 `start` 延续；将区间裁剪到窗口并对重叠取并集。将其小时数求和为 `red_hours`；**主分支红灯时间** 为 `red_hours` 和 `100 * red_hours / window_hours`。将新开启的红灯区间计为中断，单独标识在 `start` 时已开启的区间。

`mean_recovery_hours`（**平均恢复时间**）是窗口内恢复且起始已知的中断的平均完整时长。排除进行中的中断并披露其数量。无已恢复中断时为 `N/A`。初始状态未知则无法给出完整的红灯时间结论；将任何已知区间作为部分证据报告，而非假设分支初始为绿色。

## 估计的开发者影响

对每个具有观察到的同 SHA 恢复的已合并 PR 提交：

1. 将预期绿色时间设为其最早运行排队时间加上其工作流中最慢的正常时长。
2. 将观察到的绿色时间设为这些工作流首次成功完成中的最后一个。缺失成功或基线使该提交的估计不可用，而非零。
3. 将延迟从预期绿色到观察到的绿色，以上一提交的推送时间、PR 合并时间和报告窗口为界。丢弃非正区间。在每个 PR 内对重叠区间取并集。

报告受影响的已合并 PR（`blocked_prs`）、其不同的已知作者（`developers_affected`）及其 PR 等待小时数之和。这些等待是 CI 相关延迟的估计，而非合并被阻塞的证明。

对于估计的开发者工作时间，先对每个作者各 PR 的区间取并集，再跨作者求和。与用户的工作日程取交集，或明确假设工作日 09:00–18:00 UTC。返回 `blocked_working_minutes` 并除以 60 得工作小时数。单独披露作者未知的等待。不要将此估计等同于实测空闲时间、生产力损失或金钱成本。

## 校验不变量

- 唯一计数对账：分类覆盖完整时 `reliability + source + unresolved = pr_failures`；`pr_failures <= pr_executions`。
- 分子与分母共享同一总体和窗口。比率在 0% 到 100% 之间；`ci_failure_rate <= pr_failure_rate`。
- `0 <= red_hours <= window_hours`；重叠工作流绝不重复计算分支停机。进行中的中断不计入平均恢复。
- 等待结束不晚于下一次推送、合并或窗口结束。每作者的工作区间互不相交且位于所述工作日程内。
- 每个受影响 PR 必须链接到观察到的同 SHA 恢复。相关历史完整且无此类恢复时，受影响 PR、受影响作者和 CI 导致的等待时间均为零。源失败恢复时间和主分支停机不是开发者阻塞时间的输入。
- 未指定工作日程时使用文档默认值；这不算缺失证据。缺失 PR 关联或恢复时间戳才算。
- 声称的零具有完整的支撑覆盖。每个不可用指标指明其缺失输入；每个实测指标可追溯到源记录。
